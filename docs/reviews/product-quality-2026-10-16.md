## 方向与选择

[北极星说明](../design/product-north-star.md)整理现有定位和指标边界。本轮选择解决状态的可信性：它同时影响质量报表、重开检测和人工抽检，优先级高于继续增加对话能力。

真实函数探测发现 `It is not solved`、`That hasn't worked`、`How can this be fixed?`、`解决了吗？`、`以为解决了，但还是报错` 均返回确认成功。持久化将这些消息写成 `resolved_at`，且已有解决状态不会重开。另一个缺陷是人工先判解决、后改判未解决时，旧解决时间戳保留。

修复后采用完整句子的肯定表达匹配，保留常见中英文确认和礼貌表达；模糊表达不计作确认。人工改判未解决清除时间戳，不增加“用户再次求助”的重开计数。README 英文指标名称及 CLAUDE.md 认证说明同步纠正。

## 第二轮：人工交接的可信结果与并发状态

再次核实工作区后，修复下面两个已复现的 P1 问题，并覆盖此前遗漏的 Agent 和辅助查询路径：

- 没有确认工单时，中英文都明确告知转接未确认成功并给出重试方式。此处不承诺后台会继续转接，也不把提交结果不确定误写成“肯定没有工单”。
- `escalate_to_human` 返回明确的业务成败；工具审计与成功/失败指标使用真实结果。转接一旦执行便确定性结束 Agent 轮次，不再交模型改写、不继续执行后面的工具，也不再进入退款确认。最后一个模型轮次仍可执行这种不需要后续生成的转接。
- 工单创建或复用成功后，排队位置查询作为独立的尽力读取；读取失败只省略位置，保留真实工单号。位置文案按一基序号表达，避免将第 1 位误称为“前面还有 1 人”。
- 普通图与 Agent 图均输出 `handoff_outcome=queued|failed`，REST 和流式都将该结果及有效工单号保存到消息 metadata；每轮清空临时字段，后续普通回复不继承旧转接结果。`queued` 表示已确认工单，不表示人工已接通；`failed` 表示本轮未能确认成功。
- 领单使用 `UPDATE ... WHERE status='open' RETURNING`；关闭仅允许 open/claimed，并在写入时用 `coalesce` 保留既有客服归属。失去竞争的请求返回冲突，不再覆盖赢家，也不能复活已关闭工单。

数据库方案依据 [PostgreSQL 的并发更新语义](https://www.postgresql.org/docs/14/transaction-iso.html)：默认读已提交隔离下，竞争更新会针对最新行重验条件。实际测试同时覆盖 SQLite 和 PostgreSQL，不仅依赖文档推断。

验证：

- 11 项转接语义回归先失败后通过；排队查询隔离的 2 项回归和 4 项数据库竞争回归均先复现缺陷再修复。

## 第四轮：回答参考资料与历史闭环（2026-10-17）

本轮先核实了三处信息丢失：普通检索保留的修订/片段/页码被缩成文档 ID；Agent 知识工具仅返回文本和分数；历史读取丢弃了已持久化的来源。另发现实际前端位于相邻 `portfolio-fe`，其 SSE parser 会把未知命名事件当成正文。根据这些证据实施 [回答参考资料契约](../design/answer-citations.md)，没有将“模型看过这些材料”宣称为逐句事实核验。

- 普通 RAG、Agent 知识工具、FAQ 记录当时实际参考材料的白名单快照。文档保留不可变修订、片段、位置；FAQ 用内容摘要区分版本；图检索保留实体、关系、融合结果已有的独立来源集合，不拼造文档与版本配对，也不拿当前实体版本补填历史社区摘要。
- REST、持久化历史、L0/L1 缓存保留相同引用；流式仅在请求 `include_citations=true` 时发最终具名事件，旧调用默认不变。失败/中断不发布最终引用；被安全门禁改写的回答，以及标题、章节或片段需要脱敏的引用，不附上误导性的原文引用。
- 引用字段严格有界，身份字段过长则保持未知，不能截断成另一个不存在的文档；内部 metadata、上传者和临时路径不透传。旧缓存/历史没有版本时不推断绑定最新修订。
- 前端伴随修改位于 `../portfolio-fe` 的真实客服组件与 API 客户端：引用折叠展示、流式 opt-in、未知事件隔离、真实历史读取，以及避免迟到历史覆盖正在进行的新对话。初始该仓库工作区干净，未改 env、lockfile 或引入依赖。
