2026-10-28 核实：根据 [README](../../README.md) 在 `6e3bede` 中明确的企业级 Agentic RAG 客服定位及本轮产品目标，更新目标用户与当前交付形态的区分。本文保留原始整理日期、指标口径和已验证范围；定位更新不代表新增生产验证。

## 服务谁、交付什么价值

目标产品是面向企业的 Agentic RAG 智能客服系统，连接多轮业务办理、版本化知识、可追溯回答与人工交接。最终服务四类用户：

- **电商售后客户**：用中英文说明问题，获得有依据的政策答复，在多轮或中途切换问题后继续办理；需要人工时，清楚知道请求是否已记录及当前可确认的状态。
- **接单客服**：在授权范围内领取工单，查看相关会话、办理状态与回答引用，接续处理并记录结果。
- **知识与质检运营**：维护知识版本，追查回答依据与知识缺口，检查解决证据、再次求助及抽检结果，推动知识和流程改进。
- **企业集成开发团队**：通过业务工具接口接入企业系统，保留身份、权限、任务状态与可观察性边界，验证端到端办理结果。

产品价值是让客户与服务团队走完可信的客服闭环：理解问题，基于可核验知识回答，收集办理所需信息，确认后执行接入的业务操作，需要时带着上下文交接，并让运营者看见哪些问题有解决证据、哪些仍需处理。技术链路可观察、能解释、可复现，支持企业集成、运营诊断及当前公开体验的评审。

## 当前交付形态与能力边界

公开站点与项目评审体验是当前交付载体，用于验证上述客服闭环。当前已发布体验仍是单实例公共 Demo，沿用共享会话与演示身份模型。本地新版增加 `/support/` 登录工作台：客户新建私人咨询，接单客服双向回复并保存最终处理说明。私人会话在 Demo 和 strict 模式下都核对认证 owner，旧共享工单不能写私人消息；尚未部署或完成浏览器验收。升级须排空所有旧实例，细节见[私人会话合同](human-conversation.md)。

退款、退货、订单、物流与投诉业务工具目前为 mock，真实企业业务接口需要通过 ToolRegistry 接入并验证；当前不具备真实退款能力。多租户知识隔离尚未完成。企业级定位表达目标产品与架构方向，现有配置、部署模板和测试结果的证明范围仍以各自记录为准，不能据此宣布生产就绪。

质量标准体现在真实路径的一致性与诚实性：不能把模拟退款描述成真实交易，不能把没有工单的失败转接描述成成功，也不能把没有失败信号当作已解决。当前交付与后续企业集成都遵守这些标准。

## 当前开发主线（2026-10-28 用户确认）

当前以公共网站的免注册体验为主。访客由服务器签发的 Cookie 识别，仅代表持有凭据的浏览器，不声称对应现实中的特定个人。每位访客拥有独立咨询，购物与操作记录按访客主体授权；公共聊天不再以固定数字 ID 作为多人共享上下文。此项已部署到 HTTPS 公开体验；线上验证与范围见[部署记录](../operations/public-commerce-deployment-2026-10-28.md)，设计见[公共购买合同](public-commerce.md)。

已有登录客服工作台保留，后续不继续深化其功能；共享底层的必要兼容与回归不改变该方向。账号绑定和真实供应商对接作为未来扩展接口，不作为当前公共访客的前置步骤。

## 产品红线：语义决策必须由 LLM Agent 承担（2026-10-29 用户强制）

本项目的产品定位是 Agentic 智能客服。任何以下语义能力**必须由 LLM Agent 规划和决策**，禁止用关键词、正则、穷举话术、固定候选映射或本地状态机伪装：

- 请求是否属于购物、知识、售后或人工；
- 用户想买什么、用途、预算、品牌、规格和其它约束；
- 商品指代与消解，例如“1号”“第二款”“便宜的那个”“刚才那个”；
- 数量、单位、多商品与购买意图抽取；
- 信息不足时应该追问什么、先搜索还是先澄清；
- 多轮上下文中的任务切换、插问与继续；
- 工具选择、搜索条件、分页和比较策略；
- 对外部系统返回事实的自然语言解释；
- 模糊确认是否足以授权下单或付款。

新增一个自然语言表达不得要求新增一条正则、一个固定短语或一个状态迁移；否则该实现没有达到产品红线。Mock 只能模拟外部商品、购物车、报价、订单和支付接口，不能模拟或替代智能语义层。

### 观测红线：消费者消息入口之后不得有盲区（2026-10-29 用户强制）

从消费者消息进入公开聊天接口开始，路由、意图、Agent 每轮模型调用、每个工具、外部 provider 结果、持久化与最终成功/失败都必须实时输出结构化 trace。购物接管不是普通对话图的例外；任何 takeover、fallback、错误、取消或超时路径都必须先保证可观测，再保证业务继续。缺少入口 trace、只事后写 metadata、或某条业务旁路不发出实时 trace，均属线上事故级架构缺陷。

每条可变更路径的验收测试必须断言 trace 事件序列与业务结果一起存在；不能只断言文本、SQL 或最终状态。

### 千万变体评审问题（用户强制必答）

任何产品方案、架构方案或实现评审都必须先回答：

1. 当前问题的自然语言变体空间有多大，是否有限、是否封闭；
2. 该方案能否完全覆盖所有变体；若不能，覆盖率如何度量；
3. 为什么不能用穷举规则或穷举测试证明覆盖；
4. 未见过、错别字、口语、混合语言、多意图和长上下文输入下，Agent 会泛化、追问还是安全拒绝；
5. 抽样评测集如何分层、如何保持 held-out、统计置信度是多少。

自然语言问题通常有千万级以上变体。穷举规则不能覆盖，穷举测试不能证明完全覆盖；测试只能抽样估计质量，不能替代模型泛化、安全失败和线上监控。任何以“新增一个短语/正则/测试”覆盖新说法的方案，均未达到本红线。

固定 workflow 只允许出现在非语义边界，例如认证、会话归属、JSON schema 校验、外部 API 调用、幂等键、超时查询、审计、持久化、指标与展示协议。设计和实现若包含任何固定决策，必须逐项说明：为什么该点不是语义理解、为什么 LLM Agent 不适用或不足以安全承担、失败时如何诚实降级；未经用户明确批准不得采纳。生产 LLM 失败时，购物必须显式不可用或转人工/让用户稍后再试，禁止静默切换到 `SimulatedCommercePlanner` 或其它机械 planner。

2026-10-29 用户确认：既有购买实现的 simulated planner、本地购买/交易状态机和单 SKU 固定流程违反本红线，仅可视为被否决的错误方向，不得继续修补或作为后续设计基线；后续方案必须按“LLM Agent 语义编排 + 外部商业系统事实边界”重构。

既有解决确认的保守全句识别是历史质量统计边界，不是购买或通用语义决策的先例：它只在明确短语无法完全匹配时保持未确认，不推测用户含义，也不得扩展到购物、意图或实体理解。

## 北极星的计量边界

现有北极星代理指标是 **containment rate（自动处理率）**：窗口内至少收到一条机器人回复的会话中，没有人工工单且没有窗口内差评的比例。它回答“有多少会话留在自动流程内”，不能单独证明“问题已解决”。

每轮判断产品进展时必须同时检查：

- **解决证据**：`resolved_at` 代表明确用户确认或人工质检确认；AI 与人工通道的新客户消息共享同一保守确认/重开规则，客服正文或关单不是用户确认，旧消息重放也不重新改变结果；`sessions_resolved` 在服务过的会话中汇总，和 containment 分开统计。
- **再次求助**：已解决会话收到非确认消息后重开，计入 `reopened_count`。现有实现以整个会话为粒度，不能宣称能辨别同一问题或识别跨会话重开。
- **质检可见性**：没有解决证据的自动处理会话应能进入抽检；人工纠正为未解决必须撤销解决时间戳。已审核会话依现有规则退出抽检队列，复核记录不是完整审计日志。
- **质量写入归属**：私人评分在会话门闩内重新核对 owner 与原实例，SQL 写入同时绑定真实消息、父会话、实例及可评分状态；提交后的缓存清理释放门闩。质检以服务器当前证据版本和会话 key 为提案，新问题、人工接续、评分或已记录的判定变化后须刷新再评，避免旧结果覆盖新问题。见[质量写入合同](quality-mutations.md)。
- **会话实例隔离**：数字 ID 不代表同一生命周期。服务端 key、锁内校验和 journal v2 阻止旧恢复请求进入重建的私人咨询；清空先换 key/epoch，发现与重新打开不自动搬移旧稿。见[会话实例合同](session-incarnation.md)。
- **草稿与收件人连续性**：刷新/换会话/认证到期后保留可核实的原 UUID 和草稿；非空草稿不随工单关闭自动转 AI，工单变化由服务端收件约束拒绝串票；恢复和丢弃只影响本地状态，不冒称送达或撤销。见[私人会话续接合同](human-conversation.md)。
- **人工接续**：转接记录、接单、消息已提交、结束处理与客户确认解决分别核对。接单后暂停机器人；最终人工说明和关闭需同事务，旧待确认业务状态不得在关闭后复活。人工消息独立署名与存储，不冒作 AI 回复、不污染机器人指标。
- **确认业务恢复**：同一已保存提案使用稳定 UUID 和独立 SQL 账本；checkpoint 故障后重试重放原适配器结果，未知结果停止重复调用，过期/取消不能伪称撤销。该保证覆盖已初始化 API 的受保护工具，不证明外部支付 exactly-once；见[确认业务合同](durable-actions.md)。
- **任务与交接结果**：工具结果、确认状态和工单持久化必须与用户看到的承诺一致。运行探针时分别报告回复契约、已认证历史读回与客服列表只读旁证；文案、metadata、引用锚点均不能独立证明完整语义正确或真人接手。合同见[线上探针](../operations/live-probe.md)。
- **回答依据与成本**：有证据才回答，证据不足能够澄清或交接；观察延迟、模型调用预算及缓存效果，避免以牺牲正确性换取快速响应。
- **知识管理权限**：开放注册的客户不是知识运营者。Demo 与 strict 模式下，目录、修订状态、原始/规范化全文及上传、替换、重试、删除均需 active admin；客户只读检索和共享 Demo 聊天保留，管理权限不等于企业知识租户隔离。见[知识访问合同](knowledge-access.md)。
- **知识发布资格**：外部索引写入不代表发布成功。新取得的文档/图证据与知识缓存须匹配已提交的 active 版本；登记不可读不能变成 legacy 许可。已有历史快照保留，资格按证据取得时判断，不宣称跨库事务或流 token 实时撤回。旧未登记语料、失败窗口可用性和升级边界见[知识发布合同](knowledge-publication.md)。
- **监控证据**：业务代理率只用有效的新鲜统计；统计不可用和时钟偏差单独报告，不把未初始化、空窗口或旧值解释成业务失败。原仪表盘与新告警采用不同过滤，诊断按副本核对；配置、等待期与通知边界见[会话统计告警](../operations/containment-alerts.md)。
- **回复处理状态**：独立查看窗口内有 FAILED、有 COMPLETED 及最新 assistant 仍为 FAILED 的会话数。失败与完成可以重叠，技术处理完成不能替代明确解决；未持久化的请求中断还须结合流式 outcome。字段与刷新边界见[会话质量统计](../operations/session-quality-metrics.md)，既有 containment 公式不因此改变。
- **客户看到的回复**：前端失败不能被示例办理话术覆盖；只有显式流终止且正文非空才标记接收完成。部分正文、停止接收及下一轮草稿各有归属；接收完成不代表业务成功，停止也不代表业务撤销。真实反馈绑定提交成功的服务端消息 ID，仅完成的 assistant 可评分；匿名登录体验仍是独立边界。见[消息与反馈合同](message-feedback.md)。

本轮采用保守的中英文全句确认识别：接受明确的“问题解决了”“Problem solved”及礼貌前后缀；否定、疑问、引用、条件句、附带其它求助的消息不作为解决确认。未覆盖的表达保留为未确认，不调用额外模型推测解决。

外部参考：[Intercom 的结果定义](https://www.intercom.com/help/en/articles/8205718-fin-ai-agent-outcomes)区分客户确认与客户离开后的推定解决。这里采用项目自身更保守的确认口径，不照搬供应商的推定或计费规则。

## 迭代如何排序

任何方案先过产品红线：语义决策若未由 LLM Agent 承担，或固定 workflow 未逐项说明必要性和用户已批准的理由，直接拒绝，不看测试数量或实现完成度。通过红线后，优先修复会让用户被误导、实际请求丢失、任务重复执行或质量数据失真的实证缺陷；其次完善可核验的回答依据与上下文连续性；再依据评测结果扩充能力。测试通过只证明已覆盖的要求，不替代真实模型质量、真实依赖恢复或线上容量验证。

已完成的迭代包括解决状态误判、质检改判失效，以及人工转接结果的诚实反馈、并发工单生命周期保护、后端严格类型门禁、完整数据库迁移，以及回答参考资料快照贯通检索、缓存、历史和真实前端；实际前端的严格门禁、语音生命周期与可兼容的依赖修复也已完成。备份与部署失败现在可见，PostgreSQL 数据及同库 checkpoint 已经过真实恢复演练；外部检索库和完整服务恢复仍待验证。后续继续围绕可信闭环选择改进，已确认的候选与当前门禁结果见 [2026-10-16 迭代记录](../reviews/product-quality-2026-10-16.md)。
