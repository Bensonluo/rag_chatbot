# 确认业务操作与故障恢复合同

2026-10-28，本地第二十三轮。服务对象是确认退款、退货等业务办理的客户，以及需要核查执行记录的客服与企业集成开发者。默认业务工具仍为 mock；此合同不证明真实支付、远端 MCP 或生产 PostgreSQL 已通过验收。

## 提案、执行记录与回复

编译图的确定性流程和 AgentService 都在提出待确认操作时生成服务端 UUID `action_id`，与工具意图、业务参数及提出时间一同保存到 checkpoint。确认时使用原 UUID，不根据新轮次、消息或 LangGraph task ID 创建另一个执行身份。模型提供的 action/operation/scope/idempotency 字段不能覆盖服务端执行身份。

生产初始化通过 SessionCoordinator 的 session maker 注入 ActionLedger。缺少 `action_executions` 表会在构造模型/向量依赖前阻止就绪；不会退回无账本执行。内部手工构造且没有 ledger 的 ToolRegistry 保留兼容行为，不在本合同的持久保护范围。

只保护标记 `requires_confirmation=True` 的工具，目前包括默认退款、退货及导入的 MCP 写工具。查询、投诉及普通工具调用不因此获得相同保证。

确认经过当前 HTTP 认证/会话归属检查；账本绑定原会话 ID、有效 user ID、含 automation_epoch 的图 thread scope、工具名及规范化业务参数 SHA256。user/session/language 由服务端提供，语言变化不改变业务参数身份。默认退款、退货在读取旧回执前重复订单归属检查；自定义工具应提供只读 `authorize` 钩子，以抛出异常表示拒绝，并在企业适配器和远端再次执行实际授权。账本中的 Demo 有效 ID 不代表新增了真实认证能力。

首次执行必须先在独立 SQL 事务提交 `in_progress` 占位，只有成功占位的调用才进入 handler。handler 正常返回后，原始 `success/data/message` JSON envelope 经类型、JSON 和 64 KiB 大小检查，再在独立事务保存为 `completed`。它记录适配器的返回值，不表示付款结算、客户问题解决或人工接单。

| 账本观测 | 本次行为 | 客户可确认的含义 |
| --- | --- | --- |
| 无记录，提案有效且未过期 | 尝试提交占位，成功才调用工具 | 进入一次新的业务调用 |
| 匹配的 completed | 重放原 envelope，不调用 handler | 找到此前保存的结果；固定回执只展示白名单字段 |
| in_progress / unknown | 不重抢、不再次调用 | 结果尚未确认，需要人工核实 |
| 数据库不可核对 | 不发起新调用 | 本轮没有发起新操作，不能推断此前未执行 |
| UUID 与身份、scope、工具或参数不符 | 拒绝执行和读取结果 | 原请求不一致，需核实 |
| 旧提案无有效 UUID/时间/工具信息 | 拒绝执行 | 旧待确认记录不能核验，先联系人工 |

调用异常、超时或取消，返回值不可存储，以及结果提交失败，都不能作为安全重试的证据。系统尽力将占位标为 unknown；即使该更新失败，原 in_progress 也会阻止重复调用。没有超时租约、TTL 重抢或自动清理后重试。占位提交结果不明时本次不调用 handler。

## 过期、取消与审计

确认 TTL 只限制第一次执行。过期时先查账本：已保存的结果仍可重放，未知结果仍禁止重试，确实无记录时才提示重新提供办理信息并确认。取消或否认也先查记录；不能把已提交、已完成或结果未知的请求描述为已撤销或从未执行。用户需要停止后续办理，并不意味着外部请求已回滚。

恢复、未知和失败说明使用固定中英文文案，经过现有输出 guard 和流式收尾，只发送一次。不会让模型根据异常文本编造退款完成、工单成功或撤销。原业务回执中的退款/退货编号与操作 UUID 分开显示；UUID 不是支付凭证。原退款结果为需人工审核时，仍走已有真实工单创建/复用流程，只有工单提交成功才承诺请求已记录。

REST metadata 与持久化 assistant metadata 增加 `action_execution={action_id,status,replayed,tool}`，每轮清空再写入。它与业务结果内的 `status`、技术 MessageStatus 及解决指标分别使用；重放不会增加本轮 `executed_tools`。流式终止仍只表示回复处理完成。提示联系人工不会自动创建工单；客户可携操作 UUID 请求核查，授权客服可读取原对话中的说明。

## 留存与升级

本合同引入的 revision `b42f9c8e7310` 接在 `a31e8d7f6290` 之后。表以 action_id 为主键，保存绑定快照、参数摘要、状态、返回 JSON 和时间戳；原始业务参数不另外存入账本，回执本身仍可能包含敏感业务信息，应按业务审计数据管理。

删除会话只将 live_session_id 置空，保留不可变原 session scope 和执行记录；清空聊天也不删除账本。删除后不能读取旧回执或利用复用的数字 session ID 再执行。账本不是客服可直接浏览的公共 API，也不会自动清除未决记录。留存/删除政策和人工核销界面仍需企业集成进一步设计。

升级顺序：

1. 排空旧应用实例与在途办理请求，备份业务数据库；旧二进制不会执行新账本纪律，不能与新版混用以声称此保证。
2. 在受控环境执行 Alembic 升级到当前 head（第25轮为 `c53a7d9e8421`，包含本合同的 `b42f9c8e7310`），部署全部新版，再检查就绪、认证和办理路径。本文不授权实际生产迁移。
3. 对升级前无 UUID 的旧待确认记录先核查真实业务状态，不自动补 UUID 执行。它可能此前已经执行但 checkpoint 没有保存结果。
4. 任何账本行（包括 completed）都会阻止破坏性降级；PostgreSQL guard 先取表锁，SQLite guard 先取写门闩。不能删账本后退回旧镜像以消除错误，应保持新 schema 向前修复。

系统保证的范围是同一个已保存提案不会因新的 HTTP 确认或 checkpoint 故障而再次进入受保护 handler。一个新提案会生成新 UUID，不能据此判断两次业务申请是否重复。它没有实现 SQL 与外部系统的分布式事务，也不承诺外部 exactly-once；真实适配器仍需供应商幂等键、结果查询、权限与必要的 fencing。MCP 写 payload 传递服务端 UUID 为 `params.idempotencyKey`，是否兑现由供应商合同决定。
