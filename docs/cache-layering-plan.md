# 多层缓存设计方案（讨论稿，未实施）

> 状态：设计冻结备查。本文只记录 2026-09-24 架构讨论中关于缓存的结论，
> 供后续捡起时直接使用。暂不实施。

## 一、现状盘点（已有的三层，均为「管线内」缓存）

| 缓存 | 位置 | 实现 | 状态 |
|---|---|---|---|
| Embedding 缓存 | `app/services/embeddings/cached_embeddings.py` | Redis，`sha256(model+text)` key，7 天 TTL，批量 mget/pipeline，factory 默认开启 | 在用 |
| 用户事实 TTL 缓存 | `app/services/chat/user_facts_cache.py` | 进程内 per-user TTL+LRU（4096 条），带命中率指标 | 在用 |
| 图 schema 缓存 | `app/services/graph/retrieval/text_to_cypher.py` | 实例内 5 分钟 TTL | 在用（GraphRAG 开启时） |

**缺口**：没有任何「对话级」缓存——query→答案、query→检索结果、query→意图判定全部每次现算。

## 二、为什么当时没有答案级缓存

1. **demo 尺度下收益为负**：缓存价值 = 命中率 × 单次节省；QPS≈1 时绝对节省≈0，复杂度成本立刻付。
2. **正确性哲学冲突**：本项目骨架是「每次现验」（claim gate 每次重验、guardrail 每次重跑）。缓存会短路这条路径——key 不带知识库版本时，缓存的退款答案可能在政策更新后被继续端出。对政策类答案，「快但过期」比「慢但新鲜」更糟。
3. **失效原语缺失**：文档摄取路径没有单调递增的 KB 版本信号（epoch），只能靠 TTL 兜底，而 TTL 调参需要真实流量分布。
4. **演示目标是展示完整链路**（缓存命中会让链路面板的阶段消失；反过来说，一张「缓存命中」卡片本身也是好的演示素材）。

## 三、分层设计（越上层越便宜越安全）

| 层 | 缓存什么 | Key / 命中条件 | 省掉什么 | 风险 |
|---|---|---|---|---|
| **L0 精确命中** | 完整答案 | 规范化 query + KB epoch + 模型 + persona 版本的哈希 | 整条管线（~5s → ~5ms） | 近零，纯工程 |
| **L1 语义命中** | 完整答案 | query 向量（复用 L3 缓存）近邻，相似度>阈值 **且** intent+槽位签名一致 **且** 同 KB epoch | 同上 | **唯一真风险层**：换句话问政策（7天 vs 30天）可能嵌入很近 → 语义缓存只允许服务 FAQ/闲聊类意图，政策/RAG 类只走 L0 |
| **L2 检索结果** | query→chunk ID 列表 | query 哈希 + KB epoch | Qdrant+BM25 往返（~10ms） | 低；单独价值不大（大头是生成），价值在保护 Qdrant（尤其 filter-miss 双倍放大场景） |
| **L3 embedding** | 向量 | 已存在（Redis 7 天 TTL） | 向量化计算 | 已在，需补 fail-open |
| **L4 意图/槽位** | 判定结果 | query 哈希，短 TTL | light 模型调用 | 低 |
| **L5 推理侧前缀缓存** | KV cache | provider 侧 prompt caching | persona 前缀 input token 成本 | 省钱不省延迟 |

## 四、设计要点

### 1. 失效主轴：KB epoch
- 知识库内容哈希（或摄取时递增版本号）参与所有层 key。
- 文档增删 → epoch 变 → 全链路自动失效，无需逐条清理。
- 辅助两条：负反馈（点踩）立即逐出；每层挂命中率指标（复用 `USER_FACTS_CACHE_HITS/—MISSES` 模式）。

### 2. 确定性门控使缓存答案「可再验证」
claim gate 与 output guardrail 均为确定性、近零成本。缓存命中后**不盲信缓存——每次吐出前重跑一遍 gate**，用近乎免费的价格买回新鲜度保险。这是一般 LLM 缓存方案做不到的独有优势。

### 3. 铁律：fail-open（任何缓存故障不得放大为服务故障）
缓存读/写失败一律退化为直读后端。**已知违例待修**：`CachedEmbeddingService._get_redis` 连接失败直接 raise `ExternalServiceError`，会把向量检索腿打断（当前只掉到 keyword-only）——违反「缓存是优化层，永不做依赖」教条，实施本方案时一并修复。

## 五、实施前置决定（三件）

1. **KB epoch 原语**：摄取路径加内容版本信号。不加，一切靠 TTL 裸奔。
2. **L1 边界**：语义缓存允许服务哪些意图（建议 FAQ/chitchat 开、政策/RAG 关）+ 相似度阈值。
3. **写入策略**：只缓存「通过 claim gate 且带 sources 的答案」，还是模板回复也缓存。

## 六、规模意义

600 RPS 均态下，客服流量 Zipf 特性使 L0+L1 现实拦掉 50-80%（业界 FAQ 挡板率确定层 60-90%），LLM 调用从 ~1,200/s 降到几百。缓存不是性能优化项，是流量金字塔成立的底座；即使外部 LLM 产能与成本不设限，缓存仍以「5ms vs 5s TTFT」的延迟价值和「保护自有存储」的产能价值成立。

## 七、架构级补充（2026-09-24 讨论追加）

1. **减震器属性（最关键）**：客服风暴流量高度同质（支付故障 → 全员问同一句话），
   **命中率与系统压力反相关**——流量越猛，重复度越高，缓存干活越狠。缓存因此
   不只是"减速带"，是把最危险场景变成最便宜场景的"减震器"。
2. **并发流数学**：缓存命中是 ~5ms 短请求，不占 5s 长流。并发 SSE 流 =
   非命中到达率 × 5s。拦掉 80% 后：均态 3,000→600 条、高峰 8,000→1.6K、
   风暴 5-10万→1-3万。容量货币（并发流）的汇率被砍 3-5 倍。
3. **缓存救不了的**：长尾首次提问（照付 5s）；个性化轮次（带用户事实/历史的
   答案命中率≈0，**key 必须排除个性化响应或按用户隔离，否则缓存空间被无效条目淹没**）；
   KB 更新后 epoch 翻转的冷启动浪涌（需错峰预热 top-N）；延迟下限本身。
4. **多区域注意**：每区域独立缓存（数据驻留）；区域故障切换 = 冷缓存 +
   雷群全量打管线——需预热或渐进放流，不能裸切。
5. **与降级梯子的关系**：过载时按层剥：重排 → 图检索 → FAQ-only。缓存层
   （Redis + 热门答案）是"最后站着的服务层"——即使全后端不可用，热门答案
   仍可端出，这是本代码库「可用性优先」教条的终点形态。
